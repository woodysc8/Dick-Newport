# Read-only classification preview

The existing automatic classifier deliberately uses manual overrides, modern Plaid metadata and a narrow merchant rule; it never consumed legacy `category` text. Import writes legacy text separately and classifies from modern fields. The browser displays automatic classification, stored-category filters use `normalized_category`/overrides, the older weekly fallback uses stored categories, and the policy engine recalculates automatic classification. These representations can diverge. This pass exposes the differences without reclassifying financial records or changing budget inputs.

`suggestTransactionClassification` extends that same module, reusing existing modern/manual classification and adding an explicit exact-path legacy table for previews. Manual overrides win, followed by high-confidence modern evidence, legacy paths, a narrow merchant rule, and insufficient evidence. No category is inferred by broad substring matching. All suggestions without an existing manual category override require explicit approval, including high-confidence suggestions.

Legacy restaurant/rent candidates require supported outgoing amounts/accounts for medium confidence. Card payments check outgoing depository or incoming credit-card direction. Payroll supports an income candidate only for incoming depository amounts. Broker movements remain candidates, not proof of contributions. Venmo, generic payments, pharmacy, travel/ride-share and entertainment remain ambiguous. Refunds, missing direction/status/account details, and unknown metadata cannot establish confirmed spending. Pending rows remain projected.

The existing authenticated `GET /api/transactions?view=suggestions` performs owner-filtered, ordered, 500-row server reads, capped at 10,000, and returns at most 50 matching rows. Exact counts and repeated row-ID checks reject incomplete/changed coverage; database errors remain errors. Derived filters run on the server. Summary counts cover imported rows for the selected account before confidence/category/review filters. Reviewed means a manual category override; missing metadata refers to modern Plaid fields. Raw row counts include pending replacements and duplicate imports, not unique purchases or dollar totals. No raw provider transaction IDs or durable account identities are returned by this preview.

Hypothetical spending decisions use the existing budget engine with a proposed explicit category, retaining source/currency safety and current inclusion rules. Replaced pending rows and repeated provider transactions are excluded from those decisions. Credit offsets require explicit approval; no refund matching, new balance calculation, or safe-to-spend claim is made. The $420 limit, Monday–Sunday calendar and America/New_York timezone are unchanged. A successful read is not evidence of Plaid freshness. Reads are not an atomic database snapshot; concurrent same-count edits can still require refreshing the preview.

Saving remains in the existing approved transaction review/browser workflow. The new preview contains no mutation or automatic/bulk approval action. The earlier limited-period dry run remains an automatic-classifier comparison, separate from these legacy suggestions. Its label now makes that scope explicit.

The user-provided audit reports 239 rows, all normalized as `needs_review`, and no modern provider metadata. Those live counts were not independently queried during implementation. Mapping coverage does not prove any transaction's purpose. Unknown legacy paths and ambiguous candidates still need manual review. No existing tests were removed; new fixtures cover legacy mappings, direction, refunds, pending replacements, source safety, owner isolation, pagination, and absence of preview writes.

Migration history remains unchanged: user reports remote version `20261112161751` for `budget_briefing_jobs`, while the local file remains `20261112020000_budget_briefing_jobs.sql`. Do not blindly push migrations. No live financial reads/writes, Plaid calls, scheduled jobs or Google Docs publication were performed. `vercel.json` disables automatic Git deployments for this feature branch so its requested push does not deploy the application; other branches retain default behavior.
